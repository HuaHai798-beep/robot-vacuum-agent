## 二、为什么这么改（对应《上下文工程》的三条结论）

| 书的结论 | 落地 |
|---|---|
| ① 模型擅长"检索"、不擅长"统计归纳" | 步数、参数齐不齐、调了几次，**全部由代码算**，不让模型数 |
| ② 动态信息只追加、不改前缀 | 状态栏**不写 history**，只在请求末尾注入；静态前缀 92.2% 保持稳定 |
| ③ 状态要放在末尾（注意力权重最高） | `<agent_status>` 是请求最后一条消息，紧邻生成位置 |

> 为什么不是"每轮替换历史"或"持久追加"：前者会让旧状态之后的后缀重算（缓存失效），后者会堆陈旧状态。
> 本版第三种做法——**请求时注入、不落历史**：缓存只损失状态栏自身（~66 token），且永远只有一份最新状态。

## 八、原代码逐段：到底怎么做到的

### 8.1 状态栏注入：一行 `override` 决定成败

```python
# agent/tools/status_middleware.py
@wrap_model_call
def inject_agent_status(request, handler):
    if not status_enabled():
        return handler(request)                      # 关掉时零开销

    report_mode = bool(request.runtime.context.get("report", False))
    text = build_status_text(request.messages, report_mode=report_mode)
    if not text:
        return handler(request)                      # 单轮客服不注入

    messages = list(request.messages) + [HumanMessage(content=text, name=STATUS_NAME)]
    return handler(request.override(messages=messages))   # ← 只改"这一次请求"，不改 state
```

**为什么是 `request.override`**：`ModelRequest` 是不可变 dataclass，`override(messages=...)` 生成一份新请求交给下游。
**收益**：state 里的 `messages` 一条没动 → 下一轮前缀完全一致 → Prompt Cache 命中率 80.5%；同时模型永远只看到**一条最新**状态。

> 面试可讲：*"同一个需求有三种实现：每轮替换历史（破坏缓存）、持久追加（堆陈旧状态）、请求时注入（我选的）——只有第三种同时满足缓存友好和无陈旧状态。"*

### 8.2 状态从哪来：全是代码推导，不是模型自述

```python
def build_status_text(messages, report_mode=False, max_rounds=None):
    calls, args, outputs, tool_rounds = _scan_messages(messages)   # ① 扫历史
    need_report, data_like = _intent(messages)                     # ② 判意图
    if not rich and sum(calls.values()) < 2:                       # ③ 单轮不注入
        return ""
    uid, month = _user_id(outputs, args), _month(outputs, args)    # ④ 从 ToolMessage 回填
    ...
    lines = ["<agent_status …>", f"mode: {mode} | round: {round_no}/{max_rounds}", ...]
```

`_scan_messages` 只做三件事：数每个工具调了几次、记最后一次参数、记最后一次返回。
**关键**：`user_id` 只从 `get_user_id` 的**工具返回**里取（正则 `^\d{3,}$`），不从模型嘴里取——模型说错也不算数。

### 8.3 用户月份优先：T002 回归的 4 行修复

```python

user_month_used = bool(user_month) and month != user_month
if user_month_used:
    month = user_month                                 # 用户说的 > 工具算的
```

这段修好后：工具参数准确率回到 100%，全量 48/48。**这就是"状态栏注错方向会放大错误"的实证。**

## 九、模拟面试（12 问：30 秒版 + 追问 + 加分点）

### Q1. 用一分钟介绍这个项目

> 一个扫地机器人客服 Agent：RAG 知识库 + 7 个工具 + 多步编排，重点不在"能跑"，而在**可度量**——48 条评测集、九类指标、发布闸门。
> 最新 v2.4：通过率 100%、忠实度 93.8%、P95 5.71s、单次成本 0.0078 元。
> 我做的核心一件事：把"报告链路走到第几步"从提示词要求变成**代码维护的状态栏**。

**追问**：为什么是客服场景？→ 天然多轮 + 有工具 + 有数据（记录 CSV），能把 RAG、工具、记忆、评测四件事都串起来。

### Q2. 上下文工程你具体做了什么？

> 三件事：① 静态前缀固定（system + 工具定义 2465 token，占 92.2%），只追加不改写；② 动态信息统一放末尾（状态栏），吃注意力红利；③ 超阈值才压缩（工具结果清理 + 历史摘要，报告模式跳过）。
> 结果：Prompt Cache 命中 80.5%，P95 从 11.5s 降到 5.7s。

**加分点**：能说出"压缩要在两次调用之间做、别每轮都压"——这是 KV Cache 与压缩的冲突点。

### Q3. 状态栏为什么放末尾？会破坏缓存吗？

> 不会。缓存只认**前缀**：我注入的是请求最后一条消息，前缀（system + tools + 历史）一个字节没动；只有状态栏自身 ~66 token 要重算。
> 而且没有写回 state，所以下一轮历史依然干净——同时避免了"持久追加"的陈旧状态问题。

**陷阱追问**：那状态栏内容每轮变，不是也破坏缓存？→ 是，但它在前缀末尾，失效范围只有它自己，不是整个前缀；这是刻意的取舍。

### Q4. 模型要是不听状态栏怎么办？

> 状态栏只是"提示"，不是"授权"。我做了三层：① 代码算状态，模型算不出来就照抄；② 关键参数（用户 ID / 月份）落库前还有工具层校验（越权直接拦）；③ 状态栏注入失败自动降级为无状态栏，不影响主流程。

**加分点**：主动说"有损投影"——只覆盖 5 个维度，没覆盖的仍回原始消息，不删原文。

### Q5. 你提到修了个并发 bug，怎么发现的？

> 做状态栏时发现 `context_buffer` 是模块级全局 list，两个会话会互相覆盖——A 的"我家 120 平"会进 B 的改写 prompt。
> 改成 `ContextVar`；但工具在别的上下文执行读不到，所以在 `wrap_tool_call` 里再 set 一次。验证：M004 的 `rewrite_used` 从 0 恢复到 2，并发用例两个会话互不污染。

**追问**：为什么不用 threading.local？→ 异步任务在同一线程，thread-local 会串；ContextVar 跟任务走。

### Q6. 48 条 100% 通过，是不是数据集太简单？

> 不全是。48 条覆盖 6 类：检索 19、工具 10、多轮 8、安全 5、拒答 4、歧义 2；含故障注入（工具不可用）、超长工具返回、越权查询、提示词窃取、20 轮长历史。
> 而且我不只看通过率——忠实度只有 93.8%，说明还有 3 条"答对但无依据"的，那才是真问题。

**加分点**：主动指出通过率会掩盖幻觉，所以加了 judge + 数字依据率。

### Q7. 评测怎么保证不是"自己给自己打分"？

> 四条：① judge 用 deepseek-reasoner，与 agent（deepseek-chat）不同模型，交叉评审；② judge 看的是**模型实际看到的资料**（RAG trace + 工具返回），不是重新检索；③ 20 条人工标注校准，相关性 ±1 内 85%；④ 基线与判据全部版本化，跨版本拒绝横比。

### Q8. tokens_in 为什么没降？

> 诚实说：没降，+1.0%。因为静态前缀占 92.2%，报告链 5 次往返每轮重发；状态栏 +66 token/轮，靠少一轮抵消。
> 要 −30% 必须改工具契约——把 4 个取数工具合成 `get_report_data`（6 轮→2 轮），但那会改 `expect_tools` 和数据集 sha，属"口径变更版"，要重建基线。这是我 v2.5 的计划。

**加分点**：敢说"没达到目标 + 为什么 + 下一步"。面试官最烦"什么都好"。

### Q9. 如果搬到生产，你要改什么？

> 四件事：① 记忆上 checkpointer + `thread_id`，现在还没接（测试里是 skip 状态，我不装懂）；② 并发压测与超时预算；③ 成本监控（缓存命中率、单次成本进大盘）；④ 权限与审计（越权查询、提示词泄露已有拦截，但要接企业 SSO）。

### Q10. 这版最大的取舍是什么？

> 用"多一条消息"换"少一轮往返 + 不跳步"。状态栏让报告链从 5 轮降到 4 轮，忠实度 +10.5pp，代价是 tokens_in 基本持平。
> 我选择不合并工具（不做复合工具），因为它会改变评测口径；先把"不改口径能拿的收益"拿完，再动口径。

### Q11.（RAG 追问）为什么用 rerank 而不是把 k 调大？

> 块级指标显示：正确块 100% 在前 5、但挤不进前 3 → 是排序问题不是召回问题。k=5 确实能召回，但忠实度从 66.7% 掉到 43.3%（多召回噪音）。
> 官方 cross-encoder 在 k=3 下把 recall@3 拉到 100%、MRR 0.969，召回和精度同时满足。

### Q12.（行为面）你在这个项目里最"工程"的一个决定是什么？

> 加发布闸门。v2.4 第一次全量跑，通过率 95.8%，闸门直接拦下，逼我去查是状态栏把月份带偏了（T002）——如果没闸门，我可能就"看起来差不多"地发版了。
> 这件事让我确认：**没有闸门的优化，等于没有优化。**
