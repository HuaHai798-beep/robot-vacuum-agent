## 二、为什么这么改（对应《上下文工程》的三条结论）

| 书的结论 | 落地 |
|---|---|
| ① 模型擅长"检索"、不擅长"统计归纳" | 步数、参数齐不齐、调了几次，**全部由代码算**，不让模型数 |
| ② 动态信息只追加、不改前缀 | 状态栏**不写 history**，只在请求末尾注入；静态前缀 92.2% 保持稳定 |
| ③ 状态要放在末尾（注意力权重最高） | `<agent_status>` 是请求最后一条消息，紧邻生成位置 |

> 为什么不是"每轮替换历史"或"持久追加"：前者会让旧状态之后的后缀重算（缓存失效），后者会堆陈旧状态。
> 本版第三种做法——**请求时注入、不落历史**：缓存只损失状态栏自身（~66 token），且永远只有一份最新状态。

## 五、风险与回滚

| 风险 | 说明 | 处置 |
|---|---|---|
| 状态栏是"有损投影" | 只覆盖 5 个维度（user_id / month / data / calls / topic） | 按需加维度；**不要**因此删原始消息 |
| T005 仍 5 轮 | 报告链多调一次 `rag_summarize` | v2.5 复合工具收敛 |
| 相关性 −2.1pp | judge 波动 + 报告变短 | 观察项，不进闸门 |
| 缓存命中率只覆盖 DeepSeek | qwen 不返回该字段 | 报告显示 n/a，不冒充 0 |
| **回滚** | 状态栏可用 `AGENT_NO_STATUS=1` 整体关闭；并发修复属正确性，不回滚 | — |
